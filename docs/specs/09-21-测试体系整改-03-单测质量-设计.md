## 1. 目标

消除「假信心测试」——即**恒过、永不失败、或断言与实现同义反复**的用例——并按「改写优先」策略精简重复覆盖，同时补齐高价值零覆盖的真实契约。建立**可机检的质量门禁**，使回归不可能悄悄发生。

**审计基线（实测，99 文件 / 838 `it()`）**：

| 项 | 结果 |
| --- | --- |
| `.only` / `fdescribe` / `fit` | **0** 处 |
| 未 `await` 的 `.resolves`/`.rejects` | **0** 处（68 处全部已 await） |
| `toMatchSnapshot` | **0** 处 |
| 空壳用例（无任何 `expect`） | **0** 个（唯一豁免：`packages/dsh-tauri/src/client/locale/index.test.ts:196` 的 `@ts-expect-error` 类型用例） |
| blocker | **7** |
| major | **17** |
| minor / nit | ~**35** |
| 整体判定 | 「局部可疑」——多数用例是真行为测试，问题集中在四类：同义反复断言、1 处真实用户环境 I/O、`test/**` 的「源码文本 grep」套件、静默 skip 守卫 + 模块级单例隔离 |

> **机械层完全干净**是重要前提：本设计**不是**在救火，而是在处理语义层的假信心与覆盖缺口。因此**不引入** lint 规则去禁 `.only` 等已不存在的模式。

## 2. 关键决策与理由

### 决策 1：质量门禁为硬指标，覆盖率仅报告不卡关

**决定**：门禁只认**可判定的质量事实**，覆盖率**不设阈值**：

**硬门禁（必须为 0 / 必须为真）**：

1. blocker 类问题归零（见 §3.1）。
2. 「一条文档条目 ↔ 一个 `it()`」在插件/桌面端成立（子设计 02、04 共同守）。
3. 每个 `it()` 至少有一条**真实契约断言**——不得以 `toBeDefined()` / `toBeTruthy()` 收尾，不得期望值由被测实现自身表达式算出。
4. 无任何用例读写用户真实 `~/.dsh`、`~/.dsh.dev`、`.store.dat`、`.store.dev.dat`。
5. 无用例因条件守卫在门禁运行中**静默跳过**（平台受限跳过须显式登记）。

**覆盖率：生成报告，但不设阈值、不卡关**。

**理由**：本仓 `source/` 与 `archive/` 是 vendored 代码，`src-tauri/` 是 Rust，且 client 侧代码在 node 上下文基本不可测（子设计 02 §2 决策 2 已证 0/13 package 有 host-free 浏览器入口）。在这些结构性事实下，全局百分比阈值**必然逼出充数测试**，与本设计的「改写优先、不写低价值用例」直接冲突。因此覆盖率作为**可见性工具**（让人看到哪里薄、判定补测优先级），**不作为门禁**（不进 CI 卡关、不造成刷数字压力）。

### 决策 2：`@vitest/coverage-v8` 可用（**依赖由 01 声明**），仅作报告

**决定**：`@vitest/coverage-v8` **须可用**，用于生成覆盖率报告；**不**设置任何阈值，**不**作为 CI 门禁。

> **⚠️ 写入范围（执行前必读）**：`package.json`、`pnpm-workspace.yaml`、`pnpm-lock.yaml` 与 `.github/workflows/ci.yml` 的**唯一写入权归子设计 01**（见主设计 §4 共享契约）。因为 01 也要改这四个文件（加 `playwright` + CI Chromium 步骤），两个子设计并行改同批文件必然冲突。
> **因此本设计的执行方式**：**01 在同一批改动中一并声明 `@vitest/coverage-v8`**；03 **只消费**，不修改任何依赖或 CI 文件。若 03 开工时发现该依赖仍不可用，**记 blocked 上报**，不得自行改 `package.json`。

**理由**：

1. 用户明确要求「指标应该定多少」——覆盖率报告是回答该问题、并让「哪里薄」可被看见的手段，必须真的能跑出来。
2. 审计确认该包**当前未安装**，`--coverage` 不可用，因此必须显式新增依赖才能产出报告。
3. 仅作报告（决策 1）意味着新增该依赖的成本可控：它只影响本地/按需的报告生成，不改变测试通过与否的判定。

**边界（重要）**：

- **不**写入 `vitest.*.config.ts` 的 `coverage.thresholds`；**不**在 CI 中因覆盖率不达标而失败。
- 报告范围需**显式排除** `source/`、`archive/`、`test/archive/`、`src-tauri/`（vendored / Rust / 归档，非本仓被测面），否则报告数字无意义。

### 决策 3：删除策略 = 改写优先

**决定**：对审计给出的精简候选，**优先改写为真实契约断言；只有既无法改写、又确实冗余的才删除**。

**理由**：删除候选中有**整文件承载真实意图**的用例，直接删除会连契约一起丢掉：

- `test/plugin-resource-closure.test.ts:41` `describe.skipIf(!BUILT)`（`:15` `BUILT = existsSync(../src-tauri/resources/node_modules/)`）的 3 条是资源闭包契约的**唯一**覆盖，却在 CI **永远跳过**——因为 `.github/workflows/ci.yml:44-72` 的 unit job 只做 install + 建两个核心包 + typecheck/lint + `test:unit`，**从不** `build:plugins`；而唯一构建它的 `plugins-e2e` job（`ci.yml:93`）跑的是 `vitest.plugin.config.ts`（只 include `test/e2e/plugins/**/*.e2e.ts`），**不含**本文件。正确处置是**修好它在 CI 真跑**，而不是删除。
- `test/clone-profile.test.ts`（13 条）全是对 `src/ui/config/profile.tsx` 的**源码文本 grep**（`:44` 锁 Tailwind 类串、`:56` 是 `:44` 的真子集、`:77-79` 用 `source.slice(..., +500)` 魔数窗口）。其中重复与恒真的部分应删，但它守护的「profile 配置结构」意图应改写为对**真实产物/行为**的断言。

**执行规则**：

1. 对每条候选**先判定**：它守护什么契约？该契约能否用行为断言表达？
2. 能改写 → 改写（并保留原意图的语义强度，不放松断言）。
3. 确属重复（如与同文件另一条逐条重复）或恒真（同义反复）→ 删除。
4. 删除须在 `history.md` 记录**删了什么、为什么、契约是否已由其它用例覆盖**——避免"看起来精简了"。

### 决策 4：保护「不建议改」的既有约定

**决定**：以下写法**是正确的**，不得在整改中被"顺手优化"或删除：

| 项 | 理由 |
| --- | --- |
| 显式 `import { describe, it, expect }`（不用全局） | 四个 vitest 配置均**无** `globals: true`；显式导入是唯一正确写法 |
| 文件自管 mock 还原（`mockRestore()` 等） | 配置**无** `restoreMocks`/`clearMocks`，文件必须自己还原 |
| 中英混排的用例标题 | 本仓按包/层级分化的常态，非缺陷 |
| `test/**` 中带注释说明的**源码文本契约**测试（`patch-layer.test.ts`、`menu-restart.test.ts`、`clipboard-image-bridge.test.ts`、`pet-window-lifecycle.test.ts`） | 有意的**跨层守卫**（守 Rust/构建产物与 TS 侧的契约），保留 |
| `toast.test.ts` 直取内部队列（`activeQueues` / `notification.timer`） | node 环境下验证定时行为的**唯一**途径 |
| `pet-asset-headers.test.ts` 断言 `node_modules` 补丁产物 | 有意「失败要响」的补丁守卫 |
| `appimage-host-libs.test.ts` 依赖 PATH 上的 `bash` + 结构化数组解析 | Linux 打包产物的真实约束 |
| `.cssr.test.ts` 的 `not.toMatch` 负向断言 | 真实需求守卫（期望值为手写字面量，与 css-render+BEM 编译产物不同源），判为 minor 而非 blocker |
| `turnrewind/src/host/utils/lock.test.ts:313` 用 `process.platform === 'win32'` 当期望值 | 经复核为 minor（非 blocker） |

> **纪律**：整改时**只改该改的**。不得顺手重构测试结构、不得删除用户认为有价值的用例、不得为迁就实现而放松断言。

## 5. 错误语义

| 情形 | 期望行为 |
| --- | --- |
| 修完 blocker 后用例变红 | **不放松断言**：定位是实现错还是测试错，记录证据；不得为了变绿改断言语义 |
| 改写候选时发现契约不可达 | 记录到 `history.md` 并说明，再删除；不得静默删 |
| 用例单跑绿、全量红 | 判定为**用例间共享状态**（如 §3.2 #12/#13/#14 的单例与清理缺口），必须修隔离，不得靠重跑掩盖 |
| 用例单跑红、全量绿 | 同样视为隔离或顺序依赖缺陷，必须查清 |
| 怀疑某用例恒过 | 做**变异验证**：故意破坏实现，确认用例会红；不变红即确认为假信心并修 |
| 平台条件使唯一门禁用例静默跳过 | 视为 blocker（§3.2 #1 即此类），必须让它真跑 |

## 7. 验证范围

**必须实际执行**：

```bash
# 基线
pnpm test:unit -- --run

# 单文件验证（位置参数，不能用 --）
pnpm exec vitest run --project unit <file>

# 隔离性实证
pnpm exec vitest run --project unit --sequence.shuffle
```

**必须做的实证**：

1. **变异验证**（最关键）：对每条修完的 blocker，故意破坏被测实现，确认用例**会红**；恢复实现后确认会绿。不变红的即为假信心，需继续修。
2. **隔离实证**：对 §3.2 #12/#13/#14 涉及的文件，单跑绿 + 全量跑绿 才算通过；单跑绿、全量红即为共享状态缺陷。
3. **门禁实证**：确认 `plugin-resource-closure.test.ts` 在 CI 配置下**确实被执行**（检查 job 是否构建，或本地模拟该 job 的前置步骤）。

**只做静态核对**：无 `.only`；无未 await 的 `resolves`/`rejects`；决策 4 的受保护用例仍在。

**按需执行（非门禁）**：`pnpm exec vitest run --project unit --coverage` 生成一次覆盖率报告，用于**确定 §3.3 补测的优先级**与在整改报告中说明「哪里薄」；报告不参与通过/失败的判定。首次执行需先装好 `@vitest/coverage-v8`（决策 2），并确认 `source/`、`archive/`、`test/archive/`、`src-tauri/` 已排除。
