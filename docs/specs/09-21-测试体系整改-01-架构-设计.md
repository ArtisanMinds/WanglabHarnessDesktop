## 2. 关键决策与理由（含已证否方案）

### 决策 1：放弃 Vitest browser mode（`@vitest/browser-*`）

**决定**：不采用 `@vitest/browser-webdriverio` 或 `@vitest/browser-playwright` 改写 `plugin` / `desktop` project。原需求中的以下改动**全部取消**：

- ❌ `vitest.desktop.config.ts` 配置 `@vitest/browser-webdriverio` + `@wdio/tauri-service`
- ❌ `vitest.plugin.config.ts` 配置 `@vitest/browser-playwright`
- ❌ `globalSetup > test/e2e/setup-desktop.ts`（自动检测并构建 `build:debug`）
- ❌ `test/e2e/global-setup.ts` → 改名 `test/e2e/setup-plugin.ts`
- ❌ 删除 `test/e2e/support/desktop-host.ts`、`test/e2e/support/dsh-host.ts`

**理由（桌面端，NOT FEASIBLE）**：Vitest browser mode 的契约要求 provider 把浏览器导航到 **Vitest 自己的 Vite origin**：

- `node_modules/vitest/dist/chunks/cli-api.CnMVyzaz.js:11034` → `const url = new URL("/__vitest_test__/", origin)`，`:11039` → `this.browser.provider.openPage(sessionId, url.toString(), ...)`
- `@vitest/browser-webdriverio/dist/index.js:577` → `await browserInstance.url(url)`

而 Tauri webview 的文档就是应用自身（`src-tauri/tauri.conf.json:8` `"devUrl": "http://localhost:1420"`、`:10` `"frontendDist": "../dist"`）。导航到 Vitest origin 会**卸载应用文档**——被测对象消失。一个 webview 不能同时承载两套文档：Vitest 需要自己的 orchestrator 作为顶层页面（`@vitest/browser/dist/client/__vitest_browser__/orchestrator-jtzFEKPy.js` 的 `createTestIframe` 建 `iframe[data-vitest]`），而应用需要自己的文档作为顶层页面。

补充否证：

- `remote({services})` **不支持** services：整个 `remote` 函数体（`node_modules/webdriverio/build/index.js:10781-10805`）不读 `params.services`；`services` 不在 `WDIO_DEFAULTS`（`index.js:313-374`），经 `validateConfig` 被静默丢弃；service hooks 只由 WDIO runner 调用，而 `@wdio/runner` / `@wdio/cli` / `@wdio/local-runner` **均未安装**。
- wdio provider 的 `supportedBrowser` 仅 `['firefox','chrome','edge','safari']`（`@vitest/browser-webdriverio/dist/index.js:413-418`），无 tauri/wry；provider **没有**注入既有 session 的 API（`openBrowser()` 恒自建 `remote()`，`:500-523`）。

**理由（插件端，HYBRID REQUIRED）**：Vitest browser mode 的 in-page 断言 API 是**自建 JS selector engine**，根在 Vitest 自己的 `iframe[data-vitest]`：

- `@vitest/browser-playwright/dist/index.js` 的 `_createControlEngine` 走 `e.contentDocument?.documentElement`；跨源时返回 `null` → 引擎返回 `[]`，**不抛错**（静默空结果，比报错更危险）。
- `frameLocator` 只是选择器字符串 `'... >> internal:control=enter-frame'`（`@vitest/browser-playwright/dist/locators.js:70-72`），不是普适的原生跨帧。

且 13 个 package **没有一个**提供 host-free 的浏览器入口：client bundle 是 `window.__ModuleLoader__` 包裹的 CJS，依赖真实宿主的 `react` / `dsh-tauri/client` / `@deepseek-ai/*`（见 `packages/dsh-tauri-pet/dist/client.cjs:1`）。因此 browser mode 在本仓只能退化为组件级测试，无法承担「真实 dsh 宿主 UI」的端到端断言。

### 决策 2：确认真实宿主通道 = Node 上下文 + 驱动库 API

**决定**：两种真实宿主各用一条 **Node 上下文**通道：

| 层 | 宿主 | 驱动 | 运行位置 |
| --- | --- | --- | --- |
| **L2** 插件宿主 | 真实 `dsh web` 进程 + 真实 Chromium 页面 | **Playwright 库 API**（`chromium.launch()`） | Vitest `plugin` project（`environment: 'node'`） |
| **L3** 桌面端宿主 | 真实 Tauri 窗口 | **WebdriverIO + `@wdio/tauri-service` standalone API** | Vitest `desktop` project（`environment: 'node'`） |

**理由**：这正是本仓**已经**在 L3 上采用的架构，且是上游官方背书路径：

- `test/e2e/support/desktop-host.ts:25` 导入 `{ cleanupWdioSession, createTauriCapabilities, startWdioSession }`；`:236` `browser = await startWdioSession(capabilities, { rootDir: REPO_ROOT })`；`:198` `cleanupWdioSession(browser)`。
- `@wdio/tauri-service/dist/esm/index.js:4622-4738` 的 `init` 自行驱动 `launcher.onPrepare`（`:4644`）→ `onWorkerStart('standalone', ...)`（`:4646`）→ 自建 `remote()`（`:4699`）→ `service.before(...)`（`:4723`），**不需要 WDIO runner**。
- 上游文档明确此为公开路径：`@wdio/tauri-service/docs/api-reference.md:472-482`（"for use in **standalone mode or custom setups**"）、`docs/release-notes/v1.0.0.md:10`（"managing Tauri sessions **outside of the WebdriverIO runner lifecycle**"）。

因此「桌面端要不要换架构」的答案是不换：**该设计已在工作**，且换到 browser mode 反而不可行。

### 决策 3：Playwright 层不新增 Vitest project

**决定**：真实 Chromium 覆盖**不新增 project**，而是在现有 `plugin` project（node 上下文）内，用例直接 `import { chromium } from 'playwright'`，复用 `globalSetup` 已启动的真实 dsh 宿主与已换取的 Cookie。

**理由**：

1. 符合本仓既有明文约定——`docs/specs/plugin.test.md` §3.2 已写明 L2 浏览器方案为「Playwright **库 API**（`chromium.launch()`），不引入 Playwright Test Runner」。
2. 符合宿主最小化原则——`docs/testing/plugins/00-overview.md:102`「用例能复用共享宿主就绝不另起进程」；新增 project 需自带 `globalSetup`，会多起一个 `dsh web` 进程。
3. 复用 `test/e2e/global-setup.ts` 已注入的 `inject('dshBaseUrl')` / `inject('dshCookie')`，无需第二套地址交换逻辑。

**代价（已知并接受）**：浏览器用例与纯 HTTP 用例同 project，无法只跳过浏览器用例；`fileParallelism: false` 已是既有约束。

### 决策 4：`test/e2e/global-setup.ts` 不改名

**决定**：保留文件名 `test/e2e/global-setup.ts`，不改为 `setup-plugin.ts`；其内部职责按子设计 02 的需要微调（如需暴露更多已挂载插件信息），但不改名、不迁移。

**理由**：改名纯粹是需求①架构改写方案的附带产物；该方案已取消，改名无对应收益，反而制造一次无意义的引用更新面（`plugin.test.md` §4、`desktop.test.md` §3.1、`README.md` §3 三处均引用该路径）。

## 4. 边界与共享契约

### 4.1 依赖归属与共享文件写入权（关键）

**事实（实测修正）**：`playwright@1.63.0` 与 `playwright-core@1.63.0` **存在于 pnpm store**（`node_modules/.pnpm/playwright@1.63.0`），但 **`node_modules/playwright` 不可解析**（`require.resolve('playwright')` → `MODULE_NOT_FOUND`）——它只是 `@vitest/browser-playwright` 的**可选 peer**。`@vitest/coverage-v8` 同样**未安装**（不在 store，`pnpm-lock.yaml:6360` 仅记为 vitest 的 peer）。下游结论：本设计的「显式声明」不是形式要求，而是**当前代码根本 import 不到 Playwright**，不声明则 02 的浏览器用例无法运行。

**契约（本设计独占以下文件的写入权）**：

`package.json`、`pnpm-workspace.yaml`、`pnpm-lock.yaml`、`.github/workflows/ci.yml` —— 由 **01 唯一负责**，因为 01 与 03 都需要改它们（01 加 `playwright` + CI Chromium；03 加 `@vitest/coverage-v8` + CI 让 `plugin-resource-closure` 真跑），并行修改必然冲突。**01 必须一次性把两个依赖与全部 CI 改动做完**，见 §5 与 §7。

1. `playwright` **必须**显式写入根 `package.json` 的 `devDependencies`（经 `pnpm-workspace.yaml` 的 `catalogs.testing` 或直接版本，随本仓既有风格），**不得**依赖可选 peer 安装。建议加入 `catalogs.testing`（该 catalog 现含 `@wdio/tauri-service` / `vitest` / `webdriverio` / `yaml`），并在 `package.json` 写 `"playwright": "catalog:testing"`。
2. `@vitest/browser`、`@vitest/browser-playwright`、`@vitest/browser-webdriverio` **不加入**依赖（本设计不使用它们；它们因 vitest 的 peer 而存在，保持现状即可）。
3. `@vitest/coverage-v8` **必须一并声明**（版本与 `vitest` 一致 = `4.1.11`，否则 peer 不匹配）。用途仅是按需生成覆盖率报告，不设阈值、不作 CI 门禁——该策略属子设计 03 决策 2，本设计只负责把依赖装好。
4. 依赖变更须同步 `pnpm-lock.yaml`；`pnpm install` 后必须验证 `require.resolve('playwright')` 与 `require.resolve('@vitest/coverage-v8')` 均成功。

### 4.2 运行命令契约（消费方 02、04 依赖此表）

| 命令 | 实际执行 | 前置 |
| --- | --- | --- |
| `pnpm test:unit -- --run` | `vitest run --project unit` | 无（CI 需先建 `dsh-tauri` 与 `dsh-tauri-ui` 供类型解析） |
| `pnpm test:e2e:plugin -- --run` | `vitest run --project plugin` | `pnpm build:plugins`；CI 另需隔离安装 dsh CLI 并设 `DSH_E2E_DSH_BIN` |
| `pnpm test:e2e:desktop -- --run` | `vitest run --project desktop` | `pnpm build:debug`（`build:plugins` → `vite build` → `tauri build --debug --no-bundle`）；Windows only |

> **注意**：本仓脚本**不带** `run`（`package.json` 的 `test`=`vitest`、`test:unit`=`vitest --project unit` 等），交互式终端会进 watch 挂住。所有自动化与评审命令必须显式加 `-- --run`。
> **单文件过滤**：必须用位置参数 `vitest run --project unit <file>`；带 `--` 的写法不过滤，会跑完整个 project。

### 4.3 环境隔离契约（不变）

| 层 | 隔离根 | 要点 |
| --- | --- | --- |
| L2 | `DSH_E2E_HOME` | `DSH_HOME` 指向其下 scratch profile，宿主用随机端口；宿主生命周期由 `test/e2e/global-setup.ts` 统一管理 |
| L3 | home 重定向 | 重定向 `USERPROFILE`/`HOME` 一并隔离 dsh 数据与 app-data；须预建 `<home>/home/AppData/Local` 与 `AppData/Roaming`；Store 用 `.store.test.dat` |

**新增约束（Playwright 层适用）**：Chromium 的**用户数据目录必须落在隔离根内**，以免运行间状态串味。
> **实测修正（子设计 02 直接采用，勿再走弯路）**：**不能**写 `chromium.launch({ userDataDir })`——Playwright 1.63.0 会直接抛错
> `userDataDir option is not supported in 'browserType.launch'. Use 'browserType.launchPersistentContext' instead`。
> 正确写法是 `chromium.launchPersistentContext(userDataDir, { headless: true })`（已由本设计的临时探针实测通过）。
> 浏览器实例必须在用例/批次结束时可靠关闭（见 §6）。

## 5. CI 口径

`plugins-e2e` 作业的既有名称已是 `Plugins E2E Tests (vitest + playwright)`，与本设计一致，**无需改名**。本设计对其的要求：

1. 保持 `pnpm build:plugins` 前置（L2 只对构建产物运行）。
2. 保持隔离安装 dsh CLI 并设 `DSH_E2E_DSH_BIN`（`@deepseek-ai/dsh` 刻意不进依赖树，避免与 catalog 的 `@deepseek-ai/dsh-*` 形成双树）。
3. **新增**：Playwright 的 Chromium 浏览器二进制必须可用。在作业中显式安装（如 `pnpm exec playwright install chromium`）或确认 runner 已有；不得让浏览器类用例因缺二进制而静默跳过（见 §6 错误语义）。
4. `desktop-e2e` 作业口径不变（windows-latest）。

### 5.5 执行中发现的 CI 阻塞（必须修，否则上面三条 CI 改动全部形同虚设）

**现象（实测）**：`pnpm run lint` 在本分支**失败**，`✖ 117 problems (98 errors, 19 warnings)`。CI 的 `unit` 作业步骤顺序是
`install → build core packages → typecheck → Lint → Unit test`，而 `Lint` 在新增的 `build:plugins` / `Unit test` **之前**——
**lint 一失败，本设计新增的 CI 步骤与子设计 03 的「让 `plugin-resource-closure` 在 CI 真跑」全部不可达**。

**根因（实测定位）**：98 个 error **全部**集中在 `skills/test-spec/scripts/scan-tests.mjs` 单个文件（由**分支独有**提交 `df8e9969`
引入，未在 `main` 上；`main` 的 CI 因此一直是绿的）。其余 12 个文件的命中全是 warning。
`eslint.config.mjs` 的 `ignores` 列了 `docs`、`archive`，但**没有 `skills`**。

**修法（已实施）**：在 `eslint.config.mjs` 的 `ignores` 增加 `'skills'`。理由：
`skills/**` 是技能作者维护的脚本与参考文档（`skills-lock.json` 锁定上游哈希），重写以迎合本仓 lint 规约会**偏离上游并破坏哈希校验**；
且同类的 `.agents/skills/`、`.claude/skills/`、`.trae/skills/` 本就在 `.gitignore` 中，语义一致。
**不采用**「重写 `scan-tests.mjs`」或「`--fix` 改上游脚本」的修法。

**验收**：`pnpm run lint` 退出码 **0**（允许既有 warning）；CI 的 `Lint` 步骤不再阻塞后续步骤。

## 6. 错误语义

| 情形 | 期望行为 |
| --- | --- |
| `playwright` 无法解析 / 未显式声明 | **直接失败**，错误信息指明需在根 `package.json` 声明 `playwright`；不得静默跳过浏览器用例 |
| Chromium 二进制缺失 | **直接失败**并提示安装命令；不得 `describe.skip` 掉唯一覆盖 |
| 浏览器启动失败 | 用例失败并输出 launch 错误；不得退回「无浏览器则只跑 HTTP 断言」的降级路径 |
| dsh 宿主未就绪 / `globalSetup` 失败 | 整批失败（既有行为，保持） |
| 浏览器未能在用例结束前关闭 | 视为用例失败或记录为基础设施缺陷；不得留下孤儿进程 |
| 依赖传递安装的 `playwright` 被移除 | 见第一行：显式声明即消除该风险 |

**通用禁止**：任何让浏览器类用例在「门禁运行中」静默跳过的条件守卫（如依据 `existsSync` 的 `skipIf`）——门禁形同虚设。跳过只允许用于平台受限场景（如 macOS 上的桌面端用例），且须在文档中显式登记。

## 10. 开放问题

1. **Chromium 二进制在 CI 的安装方式**：`pnpm exec playwright install chromium` 会增加 CI 时长（含系统依赖）。若 runner 已预装（ubuntu-latest 通常预装 Chromium），可改为复用系统浏览器。→ 实现时实测一次决定，并在子设计 04 记录最终选择。
2. **L2 浏览器用例是否需要在 Windows 与本机也稳定**：Playwright 跨平台一致，但 dsh 宿主在 Windows 上的行为可能有差异。→ 由子设计 02 的首批浏览器用例实测暴露，不在本设计预设结论。
